# llama-cpp-prism — one local endpoint, three 27B-class models

PrismML's fork of llama.cpp running in **router mode** on a MacBook Pro (M5 Pro, 48 GB):
one OpenAI-compatible endpoint, the model picked per request, one model resident at a time,
and idle models put to sleep to free memory.

The fork is required because of **Ternary Bonsai 2 27B**, PrismML's ternary (≈1.58-bit)
re-quantisation of Qwen3.8 27B. Its `PQ2_0` / `PTQ1_0` tensor types and the Hadamard
transform its kernels need aren't in upstream llama.cpp: stock builds reject the files.

```
setup (../setup.sh)  -> install_runtime.sh    fork release tarball, pinned + SHA256 -> bin/
                     -> download_models.sh    3 models, pinned HF revisions + SHA256 -> models/
run.sh               -> llama-server router on 127.0.0.1:8888, presets from models.ini
ab.py                   speed benchmark (interleaved rounds)
quality/                quality eval: 15 code-graded tasks, Docker-sandboxed code execution
bielik_test.py          standalone check of the Polish model
```

## Models

| `"model"` | file | size | context | role |
|---|---|---|---|---|
| `bonsai2-27b` | Ternary Bonsai 2 27B, `PQ2_0` | 7.2 GB | 262144 | default: ~1.7x Qwen decode, same quality in our eval |
| `qwen3.8-27b` | Qwen3.8 27B `UD-Q4_K_XL` + vision `mmproj` | 17.6 + 0.9 GB | 262144 | images; the reference model |
| `bielik-11b-v3` | Bielik 11B v3 Instruct, `Q8_0` | 11.9 GB | 32768 | Polish-language model, a separate use case |

[`models.ini`](models.ini) is the router's preset file: `[*]` holds shared settings
(full GPU offload, `parallel 1`, q8_0 KV cache, flash attention, Jinja chat templates),
and each `[section]` is one model with its own file and context size. Keys are
`llama-server` flags without the dashes; model paths are relative, so `run.sh` `cd`s to
this directory first and a clone works from anywhere.

## Run

```sh
./run.sh            # router on 127.0.0.1:8888, holds no model until asked; Ctrl-C stops it
```

- **API**: OpenAI-compatible, `Authorization: Bearer <secrets/api-key.txt>` (generated by
  `setup.sh`, mode 0600, gitignored). Verified endpoints: `/v1/chat/completions`
  (streaming, tool calls, images), `/v1/completions`, `/v1/responses`, and `/v1/messages`
  (Anthropic format). A request for a model that isn't loaded swaps it in.
- **Router control**: `GET /models` (unloaded / loading / loaded / sleeping),
  `POST /models/load` and `/models/unload` with `{"model": "..."}`.
- **Web UI** at `http://127.0.0.1:8888/`.
- **Idle sleep** (`--sleep-idle-seconds 600`): after 10 idle minutes the engine releases
  weights and KV cache — measured 15.75 → 0.8 GiB — and the next request wakes it in a few
  seconds. Localhost only: nothing is exposed to the network.

## Supply chain

Nothing is installed from an unpinned source:

- **Runtime**: GitHub release `prism-b10735-842b188`, the prebuilt
  `llama-prism-b10735-842b188-bin-macos-arm64.tar.gz`, SHA256
  `a5c7a4d1…bb7bb` — the same digest GitHub publishes for the asset.
- **Models**: each file pinned to a Hugging Face **commit** (not a branch) and checked
  against its LFS SHA256 — `prism-ml/Ternary-Bonsai-2-27B-gguf@8b715753`,
  `unsloth/Qwen3.8-27B-GGUF@4ca72078`, `speakleash/Bielik-11B-v3.0-Instruct-GGUF@518fbbc2`.
  Downloads resume (`curl -C -`), land in `.part` files and are only renamed after the
  hash matches. Re-running re-verifies instead of re-downloading.

## Speed (2026-09-24, 3 interleaved rounds)

All configs at **262144 context**, `parallel 1`, full GPU offload, q8_0 KV, flash
attention, greedy, no speculative decoding. Decode tok/s, medians:

| model | engine | prose | code | deep (8K ctx) | prefill @8K |
|---|---|---|---|---|---|
| Qwen3.8 `UD-Q4_K_XL` | stock llama.cpp b10830 | 13.96 | 13.48 | 13.05 | 265 |
| Qwen3.8 `UD-Q4_K_XL` | PrismML fork | 13.52 | 13.19 | 12.09 | 258 |
| Bonsai 2 `PTQ1_0` | PrismML fork | 20.23 | 19.59 | 17.94 | 255 |
| **Bonsai 2 `PQ2_0`** | PrismML fork | **23.12** | **22.29** | **20.09** | 273 |

- **Model effect** (same fork): Bonsai `PQ2_0` decodes **1.66–1.71x** faster than Qwen.
  **Engine effect** (same Qwen file): the fork costs 2–7% — small, so the gap is the model.
- **`PQ2_0` beats `PTQ1_0` by ~14% despite being 21% bigger**: unpacking dense trits
  (5 per byte) costs more than the bandwidth it saves. On Metal, use `PQ2_0`.
  (Community CUDA numbers point the other way, so it's a per-backend choice.)
- **Prefill doesn't improve** (~255–273 tok/s everywhere): prefill is compute-bound, and
  ternary weights save memory bandwidth, which only decode is bound by.
- **PrismML's "lossless repack" claim holds**: `PTQ1_0` and `PQ2_0` produced byte-identical
  greedy output on every prompt.
- **Method**: configs run round-robin, not in blocks. The Mac lost ~10% from round 1 to 3
  as it heat-soaked (clamshell, vertical stand); interleaving spreads that equally, so
  the ratios hold. A first, blocked run of a different test gave non-monotonic results for
  exactly this reason.

Also tested and rejected, with numbers:

- **MTP speculative decoding** on Qwen3.8 (its built-in multi-token-prediction head):
  best case **1.10x** — not worth an extra moving part.
- **PrismML's MLX build** of the same Bonsai weights: **0.87x** the GGUF decode speed,
  ~0.8x prefill, and a higher memory peak (29.9 vs 16.4 GiB). PrismML's quoted ~28 tok/s for
  this chip was not reproduced by either runtime (best round 25.3).

## Memory at 262K context

| model | RSS | weights on GPU | KV cache | compute |
|---|---|---|---|---|
| Qwen3.8 `UD-Q4_K_XL` | 25.3 GiB | 15.35 GiB | 8.50 GiB | 1.36 GiB |
| Bonsai 2 `PQ2_0` | 16.6 GiB | 6.70 GiB | 8.50 GiB | 1.36 GiB |

Same architecture (Qwen3.8's hybrid attention + gated-delta-net blocks), so the KV cache is
identical, and for Bonsai it is now the largest item. The KV cache is reserved in full at
load: memory doesn't grow as a conversation fills up. The GPU can address ~37 GiB of the
48 GB, so either model fits at full context with room to spare.

Context in practice: a full 262K prompt is roughly a 400–600-page book, and takes 20+ min
to prefill cold. llama.cpp's prompt cache makes follow-ups cheap: a 20K-token document took
88 s for the first question, then **7 s and 4 s** for the next two (39 new tokens each).

## Quality eval (2026-09-25)

Speed is only useful if the answers hold up, and PrismML's "near-lossless" claim was
self-reported. [`quality/`](quality/) runs 15 English tasks through the router with
identical settings for both models (temp 1.0, top_p 0.95, top_k 20, min_p 0.05,
`reasoning_effort: medium`, two seeds):

| area | tasks | how it's graded |
|---|---|---|
| reasoning / maths | 6 | exact answer; every ground truth computed in code, never typed |
| code | 3 | model's function run against hidden tests in a Docker sandbox (`--network none`, read-only, 256 MB, 1 CPU, 64 pids, no-new-privileges) — incl. finding a planted bug |
| structured output | 1 | invoice → JSON, field by field |
| tool calls | 2 | single call + parallel calls, arguments checked |
| instruction following | 1 | format constraints, checked mechanically |
| long context | 1 | find a code in ~60K tokens of decoys |
| explainer | 1 | word limit checked in code; content scored by hand against a 6-point rubric |

**Result: Qwen 29/30, Bonsai 30/30, rubric 11/12 vs 11.5/12 — no quality difference
detectable — while Bonsai took about half the time per task (35 vs 66 s median) at
similar thinking length.** No response was truncated, empty or looping. Full report,
including every failure checked by hand: [`results/quality-20260925-091013/REPORT.md`](results/quality-20260925-091013/REPORT.md).

The honest caveat is in the report too: both models are near 100%, so this set can't
separate them. Multi-step agentic tool loops — where PrismML's own known-issues list
says ternary models struggle — are untested.

```sh
python3 quality/run.py [--rounds N] [--only M1 C3 ...]   # needs ./run.sh up and Docker
python3 quality/regrade.py results/quality-<stamp>        # re-grade saved answers, no model calls
python3 ab.py --rounds 3                                  # speed; stop ./run.sh first
```

`regrade.py` exists because a grader bug was found mid-run (a correct Polish answer
failed a too-strict language check): fixes are re-applied to every saved answer from
every model, so no model gets a correction the other didn't.
